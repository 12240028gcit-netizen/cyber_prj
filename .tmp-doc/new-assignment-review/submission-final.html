A. Application Overview

The Secure Student Club Registration and Membership Management System provides a web-based process for students to join campus clubs. Students create an account, sign in, browse active clubs, submit membership applications, and check request status. Club administrators review requests, approve or reject pending applications, create or edit clubs, set capacity, and view approved members.

The application has two roles: Student and Club Administrator. Students can view their own applications. Administrator routes require a signed-in admin role. Authorization is enforced by the Express API, not only by hiding browser controls.

Technology and features

  • Frontend: HTML, CSS, and browser JavaScript in public/index.html, public/styles.css, and public/app.js.
  • Backend: Node.js and Express in server.js; SQLite stores users, clubs, applications, and sessions.
  • Security libraries: bcryptjs, express-session, connect-sqlite3, Node crypto, Zod, Helmet, express-rate-limit, and Winston.
  • Student features: registration, login, logout, club browsing, application submission, and status tracking.
  • Admin features: application review, club creation/editing, capacity management, and approved-member listing.

Not implemented in this version: profile editing, password reset, email verification, per-club admin assignment, automated backup/recovery, and production deployment.

System and cyber flow

Browser request -> security middleware -> session / CSRF -> input validation -> role authorization -> parameterized SQLite -> authorized response -> HTML output encoding

Registration validates data, hashes the password with bcrypt, encrypts selected student identity fields, and creates a fresh session. Login compares the password against the stored bcrypt hash and regenerates the session ID. Admin responses decrypt selected identity fields only after admin authorization. Winston records important events.

1. User authentication and authorization

Registration validates input, checks for a duplicate email digest, hashes the password with bcrypt cost 12, encrypts selected identity data, assigns the student role, and creates a regenerated session. Login looks up the user, compares the supplied password with the bcrypt hash, uses a generic failure response, and regenerates the session ID on success. Login/registration attempts are rate-limited. Authentication middleware returns 401 for signed-out requests; role middleware returns 403 when the signed-in role is not allowed. Student application queries are scoped to the current user ID.

Code locations: server.js registration/login handlers, auth and role middleware, /api/applications, and /api/admin/*; browser form handling is in public/app.js.

Figure 3. Password hashing and role checks. Annotated excerpts from server.js. bcrypt.hash stores a one-way hash; bcrypt.compare verifies the password; auth and role middleware protect routes.

2. Data encryption and protection

Names, emails, and student IDs are encrypted at rest with AES-256-GCM using a random 12-byte IV and an authentication tag. DATA_ENCRYPTION_KEY is read from the private environment file. A keyed HMAC of the normalized email is used for account lookup without a plaintext email index. Passwords are bcrypt hashes, not reversible encryption. Database helpers bind query values.

Limits: only selected identity fields are encrypted. The complete SQLite database file, backups, logs, and host filesystem need separate access controls. The same key is currently used for AES and email HMAC; a stronger design would derive separate keys. Losing the key makes stored identity values unrecoverable. Never include .env or real student details in screenshots or shared archives.

Figure 4. AES-GCM protection. Source excerpts show cipher creation, authentication-tag use, decryption, and protected database columns. No secret key or real student record is shown.

3. Input validation and output sanitization

Zod schemas validate email, password, name, student ID, messages, club fields, capacity, and allowed application decisions. Server-side validation occurs before database operations. Request bodies are limited to 20 KB. SQL values use bound parameters. Browser code escapes HTML-significant characters before inserting dynamic text. Helmet applies a restrictive Content Security Policy. HTML form constraints improve usability but are not the security boundary.

The project uses contextual HTML encoding in its escape helper; it does not include a separate DOMPurify dependency. Describe the implemented technique accurately as output encoding.

Figure 5. Validation and output encoding. Annotated excerpts show a Zod schema, validation middleware, bound SQL values, CSP, and browser escaping.

4. Session management

Sessions are stored in SQLite with a 30-minute rolling maximum age. Cookies use HttpOnly and SameSite=Strict; Secure is conditional on production mode or direct TLS. Login and registration regenerate the session ID. State-changing requests require a random session-bound CSRF token checked with a timing-safe comparison. Logout destroys the server-side session and clears its cookie.

Current local limitation: development mode is configured and TLS key/certificate paths are empty. The local connection is HTTP, so a Secure cookie is not demonstrated.

Figure 6. Session and CSRF controls. Annotated source excerpts show cookie attributes, expiry, CSRF validation, session regeneration, and logout invalidation.

5. Error handling and logging

Winston writes timestamped structured events to logs/security.log and the console. Events include login outcomes and key registration, application, and club actions. A central error handler returns a generic message rather than a stack trace or database error. Internal error messages are logged, so restrict access to log files.

Figure 7. Logging and safe errors. Annotated excerpts show Winston setup, security event records, and a generic client-facing error.

6. Secure communication

The application can create an HTTPS server when both TLS key and certificate paths are valid. Otherwise it starts HTTP. Production can terminate TLS at a trusted reverse proxy; TRUST_PROXY should only be enabled behind such a proxy. The application does not itself enforce an HTTP-to-HTTPS redirect. Current local development uses HTTP, therefore HTTPS is not evidenced as active.

Likely questions

Why bcrypt? It stores a one-way hash and makes password guessing more expensive. Why AES-GCM? It encrypts selected personal data and detects tampering. Why server-side RBAC? Browser controls can be bypassed, so each protected API checks authorization on the server. What does CSRF protection do? It requires an unpredictable token tied to the user session for state-changing requests. What testing is complete?
